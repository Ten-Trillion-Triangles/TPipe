## 1. Overview

The TPipe GraalVM Native ABI exposes C-exported entry points for interop with Python, Node.js, and other language runtimes. Some of these entry points (the "phantom reference functions") have Kotlin implementations in `src/main/kotlin` — but others are C-native functions that must be generated by the GraalVM Native Image compilation process itself, because they operate at the boundary between the native image runtime and the guest language runtimes.

This document describes the bootstrap process — how TPipe's native image is built and how the 8 phantom reference functions get their C entry points.

---

## 2. The 8 Phantom Reference Functions

These functions are spec'd in the ABI but have no Kotlin implementation in `src/main/kotlin` — they are native image entry points:

| Function | Type | Native Image Behavior |
|----------|------|----------------------|
| `TPipe_init()` | Library init | Generated by GraalVM SDK native-image tool via `@CEntryPoint` annotation |
| `TPipe_shutdown()` | Library shutdown | Same |
| `TPipe_getState()` | State query | Same |
| `TPipe_Handle_addRef()` | Handle lifecycle | Same |
| `TPipe_Handle_release()` | Handle lifecycle | Same |
| `TPipe_Handle_getRefCount()` | Handle diagnostics | Same |
| `TPipe_Handle_isValid()` | Handle validation | Same |
| `TPipe_getCapabilities()` | Capability query | Returns static struct compiled into native image |

These do NOT exist as Kotlin classes in `src/main/kotlin`. They are generated by the GraalVM Native Image tool via `@CEntryPoint` annotations on special bootstrap objects.

## 3. How GraalVM Native Image Entry Points Work

### 3.1 The Mechanism

GraalVM Native Image can export Kotlin/Java methods as C functions via the `org.graalvm.nativeimage` API:

```kotlin
import org.graalvm.nativeimage.*
import org.graalvm.nativeimage.c.*

class TpipeBootstrap {
    @CEntryPoint
    companion object Bootstrap {
        @JvmStatic
        fun TPipe_init(thread: IsolateThread): Int {
            // Called by native code before any other TPipe API
            return TpipeNative.init(thread)
        }

        @JvmStatic
        fun TPipe_getState(thread: IsolateThread): Int {
            return TpipeNative.getState(thread).ordinal
        }
    }
}
```

The `@CEntryPoint` annotation tells the GraalVM native image compiler to generate a C-compatible function symbol. The generated symbol is:
- Exported in the native image's symbol table
- Callable from C code (Python ctypes, Node FFI, etc.)
- Bound to a specific isolate thread context

### 3.2 Isolate Thread Context

Each native image runs inside a GraalVM **Isolate** — an isolated native heap with its own GC. All C entry point functions receive an `IsolateThread*` as their first argument, which is the execution context for that call. TPipe uses this to:
- Store library state in the isolate's local storage
- Provide thread-safe initialization via `IsolatedToken` locks
- Clean up on isolate shutdown

```c
// C caller perspective:
int result = TpipeBootstrap_TPipe_init(isolate_thread);
TPipe_LibraryState state = TpipeBootstrap_TPipe_getState(isolate_thread);
```

### 3.3 Automatic Symbol Generation

The GraalVM SDK generates symbols using the Java method's class and name:
- `TpipeBootstrap.TPipe_init(IsolateThread)` → symbol `TpipeBootstrap_TPipe_init`
- `TpipeBootstrap.TPipe_shutdown(IsolateThread)` → `TpipeBootstrap_TPipe_shutdown`
- etc.

The `IsolateThread` parameter is implicit in C — callers just pass the isolate pointer.

## 4. TPipe Bootstrap Architecture

### 4.1 Bootstrap Class Location

Create `TPipe/src/main/kotlin/Native/TPipeBootstrap.kt`:

```kotlin
package TPipe.Native

import org.graalvm.nativeimage.*
import org.graalvm.nativeimage.c.*
import org.graalvm.nativeimage.c.constant.*
import org.graalvm.nativeimage.misc.*

class TPipeBootstrap private constructor() {
    companion object {
        private val state = AtomicReference<LibraryState>(LibraryState.LOADED)
        private val initLock = ReentrantLock()

        @CEntryPoint
        @JvmStatic
        fun TPipe_init(thread: IsolateThread): Int {
            if (state.get() == LibraryState.READY) return TPIPE_OK
            initLock.withLock {
                if (state.get() == LibraryState.INITIALIZING) return TPIPE_OK // concurrent no-op
                state.set(LibraryState.INITIALIZING)
                try {
                    TpipeRuntime.initialize()
                    state.set(LibraryState.READY)
                    return TPIPE_OK
                } catch (e: Throwable) {
                    state.set(LibraryState.SHUTDOWN)
                    return TPIPE_ERR_OUT_OF_MEMORY
                }
            }
        }

        @CEntryPoint
        @JvmStatic
        fun TPipe_shutdown(thread: IsolateThread): Int {
            initLock.withLock {
                if (state.get() == LibraryState.SHUTDOWN) return TPIPE_OK
                state.set(LibraryState.SHUTTING_DOWN)
                TpipeRuntime.shutdown()
                state.set(LibraryState.SHUTDOWN)
            }
            return TPIPE_OK
        }

        @CEntryPoint
        @JvmStatic
        fun TPipe_getState(thread: IsolateThread): Int {
            return state.get().ordinal
        }

        @CEntryPoint
        @JvmStatic
        fun TPipe_getCapabilities(thread: IsolateThread, caps: CapabilityStruct): Int {
            caps.set(
                hasPipelines = true,
                hasDistGrid = true,
                hasManifold = true,
                hasPCP = true,
                hasMemory = true,
                hasP2P = true,
                hasListHandles = true,
                hasMapHandles = true,
                hasStreaming = true,
                hasJsonContent = true,
                hasBinaryContent = true,
                gcType = getGCType()
            )
            return TPIPE_OK
        }

        @CEntryPoint
        @JvmStatic
        fun TPipe_getVersion(thread: IsolateThread, buffer: CharPointer, len: Int): Int {
            val version = "0.2.0" // sync with build config
            val bytes = version.toByteArray()
            if (len < bytes.size + 1) return TPIPE_ERR_BUFFER_TOO_SMALL
            buffer.writeBytes(bytes, bytes.size)
            buffer[bytes.size] = 0
            return TPIPE_OK
        }

        @CEntryPoint
        @JvmStatic
        fun TPipe_isInitialized(thread: IsolateThread): Int {
            return if (state.get() == LibraryState.READY) 1 else 0
        }
    }
}
```

### 4.2 Handle Table Access via Native Image C API

For `addRef`/`release`/`getRefCount`/`isValid`, the bootstrap uses `org.graalvm.nativeimage.c` to interact with the Kotlin handle table:

```kotlin
class TPipeHandleBridge {
    companion object {
        private val handleTable = HandleTable // internal singleton

        @CEntryPoint
        @JvmStatic
        fun TPipe_Handle_addRef(thread: IsolateThread, handleId: Long): Int {
            return handleTable.addRef(handleId).also {
                if (it < 0) return TPIPE_ERR_INVALID_HANDLE
            }
        }

        @CEntryPoint
        @JvmStatic
        fun TPipe_Handle_release(thread: IsolateThread, handleId: Long): Int {
            val freed = handleTable.release(handleId)
            if (!freed) return TPIPE_ERR_INVALID_HANDLE
            return TPIPE_OK
        }

        @CEntryPoint
        @JvmStatic
        fun TPipe_Handle_getRefCount(thread: IsolateThread, handleId: Long): Int {
            return handleTable.getRefCount(handleId)
        }

        @CEntryPoint
        @JvmStatic
        fun TPipe_Handle_isValid(thread: IsolateThread, handleId: Long): Int {
            return if (handleTable.isValid(handleId)) 1 else 0
        }
    }
}
```

## 5. Build Process

### 5.1 Gradle Native Image Task

In `TPipe/build.gradle.kts`:

```kotlin
import org.graalvm.sdk.nativeimage.*

plugins {
    id("org.graalvm.buildtools.native") version "0.10.0"
}

nativeImage {
    agent = true  // enables dynamic tooling support
    mainClass = "TPipe.Native.TPipeBootstrap"
    buildArgs.addAll(listOf(
        "-H:+ReportExceptionStackTraces",
        "-H:+ShutdownOnExitHook",
        "-H:-DeleteNativePoints",
        "--enable-https"
    ))
    metadataRepository {
        enabled = true
    }
}

// Force static initialization for consistent behavior
tasks.withType<org.graalvm.buildtools.native.tasks.NativeImageTask> {
    nativeImageWorkDirectory.set(file("${project.buildDir}/native-image"))
}
```

### 5.2 Build Command

```bash
./gradlew :TPipe:nativeImage
# Produces: TPipe/build/native/nativeImage/TPipe (executable/shared library)
```

### 5.3 Generated Symbols

After building, the native image exposes these C symbols (verifiable via `nm` or `objdump -T`):

```
nm -D build/native/nativeImage/TPipe | grep TPipe_
# TpipeBootstrap_TPipe_init
# TpipeBootstrap_TPipe_shutdown
# TpipeBootstrap_TPipe_getState
# TpipeBootstrap_TPipe_Handle_addRef
# TpipeBootstrap_TPipe_Handle_release
# TpipeBootstrap_TPipe_Handle_getRefCount
# TpipeBootstrap_TPipe_Handle_isValid
# TpipeBootstrap_TPipe_getCapabilities
# TpipeBootstrap_TPipe_getVersion
# TpipeBootstrap_TPipe_isInitialized
```

### 5.4 Symbol Name Sanitization

GraalVM generates symbols in `ClassName_MethodName` format. For cleaner C API names (TPipe_init, not TpipeBootstrap_TPipe_init), use `@CEntryPoint(name = "TPipe_init")` explicitly:

```kotlin
@CEntryPoint(name = "TPipe_init")
@JvmStatic
fun tp_init(thread: IsolateThread): Int
```

This is the recommended approach to match the ABI spec's naming convention exactly.

## 6. Isolate Lifecycle and Handle Cleanup

### 6.1 At-Exit Hook

The native image's built-in at-exit hook (`-H:+ShutdownOnExitHook`) automatically calls the shutdown path when the host process exits, preventing resource leaks in embedded scenarios. However, explicit `TPipe_shutdown()` is still recommended for clean termination of long-running pipelines.

### 6.2 Handle Cleanup on Shutdown

When `TPipe_shutdown()` is called:
1. All in-flight operations are cancelled
2. All outstanding handles have their refcounts decremented to 0 (via `TPipe_Handle_release` on each)
3. The handle table is cleared
4. Thread pool is shut down
5. Library state moves to `SHUTDOWN`

This ensures no dangling handles survive process shutdown.

## 7. Python/Node.js Binding Generation

### 7.1 Symbol Resolution

Python (ctypes) and Node.js (FFI) bindings use the native image's exported symbols directly:

```python
import ctypes

lib = ctypes.CDLL('./libtpipe.so')  # native image as .so
init = lib.TPipe_init
init.restype = ctypes.c_int
init.argtypes = [ctypes.c_void_p]  # IsolateThread*

# Node.js similarly via FFI
```

### 7.2 IsolateThread Acquisition

The first call to `TPipe_init` must pass a valid `IsolateThread*`. Hosts can:
- Use `GraalIsolate#newIsolate()` to create one
- Pass `nullptr` for single-isolate programs (bootstrap class initializes a default)
- Use the default isolate from `IsolateThread.current()` inside the native image

## 9. Annotation Retention Audit

### 9.1 Why This Matters

GraalVM's static analysis can only see annotations with `RUNTIME` retention. Annotations with `SOURCE` or `CLASS` retention are invisible to the native image compiler — binding operations that rely on annotation scanning (e.g., JSON serialization bindings, DI wiring, PCP function registration) fail silently at runtime in native images.

On the JVM, all retention levels are accessible at runtime. On native images, only `RetentionPolicy.RUNTIME` annotations survive static analysis.

### 9.2 Required Audit Checklist

For each TPipe binding annotation used in the reflection/dispatch path, verify the retention:

| Annotation | Location | Expected Retention | Verify |
|------------|----------|-------------------|--------|
| `@JsonProperty` | P2PDescriptor JSON binding | RUNTIME | ☐ |
| `@JsonIgnore` | P2P payload fields | RUNTIME | ☐ |
| `@JvmClass` / `@JvmName` | ManifoldDefaults.kt Class.forName | RUNTIME | ☐ |
| Custom `@Binding` | FunctionRegistry registerFunction | RUNTIME | ☐ |
| `@Inject` (DI) | Any injection points | RUNTIME | ☐ |
| `@Component` | TPipe bean registration | RUNTIME | ☐ |
| PCP binding annotations | PipeContextProtocol options | RUNTIME | ☐ |

### 9.3 Action Required

1. Audit each annotation class — confirm `RetentionPolicy.RUNTIME` is declared
2. If any annotation has `RetentionPolicy.SOURCE` or `RetentionPolicy.CLASS`, change to `RUNTIME`
3. After any annotation change, rebuild native image and re-run ServiceLoader verification (Section 10)

### 9.4 Jackson + Kotlin Annotation Gotcha

Kotlin data classes combined with Jackson use `@JsonProperty` from `com.fasterxml.jackson.annotation.JsonProperty`. Verify this dependency's annotations are at RUNTIME retention (they are by default, but verify in TPipe's jackson-databind version).

## 10. ServiceLoader SPI Discovery — Native Image Requirements

### 10.1 The Silent Failure Problem

`ServiceLoader.load(SomeInterface.class)` is Java's plug-in discovery mechanism. TPipe uses it for `Pipe`, `Connector`, `Splitter`, `Manifold`, and agent implementations.

**On JVM:** Returns a populated iterator if META-INF/services/* files exist on the classpath, or empty iterator if no providers — no exception thrown in either case.

**On Native Image:** If the META-INF/services/* files are not registered in `resource-config.json`, the ServiceLoader returns an **empty iterator with no exception**. The application silently has zero service providers — it appears to work but does nothing.

This is the most dangerous native image failure mode: **silent, no error, no exception**.

### 10.2 Required resource-config.json Entry

In `TPipe/src/main/resources/META-INF/native-image/resource-config.json`:

```json
{
  "resources": [
    { "pattern": "META-INF/services/*" }
  ]
}
```

This ensures all service provider files are bundled into the native image and ServiceLoader can find them.

### 10.3 Startup Verification (Required)

In `TPipeBootstrap.TPipe_init()`, add verification after runtime initialization:

```kotlin
// After TpipeRuntime.initialize() in TPipe_init()
val testProviders = ServiceLoader.load(com.TTT.Pipeline.Pipe::class.java).iterator()
if (!testProviders.hasNext()) {
    throw IllegalStateException(
        "TPipe native image startup failure: no Pipe service providers found. " +
        "Ensure META-INF/services/* entries are registered in resource-config.json. " +
        "See graalvm-abi-reflection-config.md §9 for details."
    )
}
```

This makes ServiceLoader failure **audible** (clear exception, actionable message) instead of silent.

### 10.4 Graceful Degradation Option

If some providers are optional, use this pattern:

```kotlin
val providers = ServiceLoader.load(OptionalService::class.java).toList()
if (providers.isEmpty()) {
    logger.warn("Optional service X not found — using default implementation")
} else {
    selectedProvider = providers.first()
}
```
